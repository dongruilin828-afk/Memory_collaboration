📈 1. 进程总结
初始目标与尝试：从“先不考虑形式，先跑通功能”出发，使用 Python 编写自动化脚本来抓取 AI 共享对话链接中的内容。
技术选型与实现：选用了 Playwright 搭配 BeautifulSoup 来抓取和解析动态网页内容。
问题解决与迭代：
解决图片抓取与渲染问题：早期遇到过豆包的图片成功保存到本地 images 文件夹中、但未能在 Markdown 中正确渲染的问题，随后修复了图片提取逻辑。
解决抓取超时问题：在抓取 ChatGPT 页面时，使用 Edge (msedge) 作为浏览器内核时遇到长达 180s 的启动/网络等待超时。随后切换为 Playwright 默认的无头 Chromium 模式，并修改了等待策略，问题得以解决。
兼容多平台：在原有豆包抓取的基础上，加入了对 ChatGPT 链接格式的兼容。
成果输出：生成了高质量的 AI_memory_export.md 文件，成功将对话分离成了“👤 用户”与“🤖 AI 回答”，并能将历史对话、包括讨论课个人作业的分析结果都留存记录下来。最后进行了 Git 提交（包括“支持图片”、“支持豆包和ChatGPT”、“删除无用文件”等 commit），并合并到了 main 分支。
💡 2. 经验总结
规避 networkidle 陷阱：在抓取现代单页应用 (SPA) 如 ChatGPT 时，由于后台长连接的存在，依靠 wait_until="networkidle" 往往会导致超时。我们在代码中加入了 Try-Except 进行优雅降级，当网络等待超时时程序能继续往下走。
基于 DOM 元素的等待更加稳定：我们发现通过等待特定的 CSS 选择器（如 page.wait_for_selector(".message-item, [data-message-author-role]")）出现，比单纯等待网络状态更为可靠且高效。
清晰的数据结构是后续处理的前提：将爬取下来的无序 HTML 节点依据 data-message-author-role 进行角色切分，然后统一映射到 Markdown 模板中，这种模块化的数据清洗方式非常便于后续将内容输入给其他 AI 去做进一步的总结和分析。
⚠️ 3. 教训与反思
依赖浏览器的自动化比较脆弱：由于直接依赖 Playwright 模拟浏览器行为，一旦官方页面（如 ChatGPT 或 豆包）的 DOM 结构或者 Class 命名发生改变，解析器（parser.py）就极易失效，需要经常维护。后续（正如工作文档中所提）需要探索直接使用官方 API 来拉取对话数据，这才是最稳定的长期方案。
本地路径与相对路径的引用坑：在处理多媒体（如抓取下来的图片）时，Markdown 中的图片引用稍有偏差（比如漏掉相对路径的层级），就会出现“图片在硬盘上但 Markdown 渲染不出来”的现象，处理静态资源链接时必须格外严谨。
总体而言，那是一次非常高效的原型开发（Proof of Concept）过程。虽然存在一些自动化的坑点，但最终成功实现了核心链路，并输出了格式优美的对话记忆记录。
4. 你还要记住，ChatGPT是滚动到对应位置才把对话渲染出来，我们之前尝试过使用超长窗口解决该问题，但这又导致用户登录时浏览器显示错位，我们解决这个问题的办法是对视口（Viewport）的大小进行条件判断，根据“是否需要用户手动登录”来动态设置窗口高度：登录模式下使用默认正常窗口： 当我们检测到处于需要手动登录的模式（need_login = True，此时浏览器是带有 UI 界面的）时，我们会将 viewport_config 设为 None，并在 Playwright 启动参数中传入 no_viewport=True。这会让浏览器以默认大小和原生视口启动，从而保证网页的 UI 和登录弹窗正常居中，不会发生错位。
抓取模式下使用超高虚拟窗口： 当我们处于后台静默抓取模式（headless=True）时，我们不需要考虑登录界面的美观，只需要让 ChatGPT 以为我们在往下滚动从而把历史记录都渲染出来。因此此时我们会强制设置 viewport={'width': 1920, 'height': 10800}，将页面视口拉得极高，一次性把通过虚拟列表（Virtual List）隐藏的聊天内容全部“挤”进渲染流里。

7. 平台适配器模块化约定（2026-08-11）
为了避免所有平台逻辑继续堆积在 parser.py 中，ChatGPT、DeepSeek、豆包已经迁移到 providers 目录。parser.py 只负责浏览器启动、页面加载、通用图片下载、平台调度、降级解析和命令行入口；markdown_exporter.py 统一负责终端展示与 Markdown 导出。

每个平台模块统一提供以下成员：
- DISPLAY_NAME：终端显示的平台名称。
- WAIT_SELECTOR：判断动态消息节点是否出现的稳定选择器。
- parse_messages(soup, image_map)：识别并解析该平台；不属于该平台时返回 None。
- collect_html(page)：仅虚拟列表平台需要实现，用于逐屏采集完整消息。

新增 AI 时，应在 providers 中新建独立文件，再在 providers/__init__.py 中导入并加入 PROVIDERS。平台检测顺序由 PROVIDERS 决定；当前顺序必须保持为 ChatGPT、DeepSeek、豆包，除非有充分测试证明可以调整。不要把新平台的 CSS 选择器、附件规则或消息清洗逻辑重新写回 parser.py。

模块拆分属于纯重构时，必须完整运行 run_tests.py，并与 results_right 中的黄金基线比较。图片链接可能包含动态签名，不能只比较原始文件哈希；应同时比较问答数量、忽略本地图片文件名后的正文、图片文件是否存在，以及超长对话的首尾和多个中段抽样点。
8. Gemini 多模态分层总结约定（2026-08-11）
API 总结层必须与网页平台解析层解耦。providers 只负责把不同平台统一成 role/content 消息；gemini_summarizer.py 只消费统一消息，不得包含 ChatGPT、DeepSeek 或豆包的 DOM 选择器。这样以后新增平台或更换总结模型时，两边都不用互相修改。

密钥只允许从环境变量读取：Gemini 使用 GEMINI_API_KEY；SiliconFlow 使用 Silicon_API_KEY（兼容 SILICONFLOW_API_KEY）。禁止把密钥写入源码、README、日志、异常全文、命令参数、JSON 输出或 Git 配置。后端与模型名从 SUMMARY_PROVIDER、SUMMARY_MODEL（兼容 GEMINI_MODEL）或命令行参数读取，默认值只是当前选择，不得在业务调用点重复写死。

多模态总结采用分层管线：
- 程序负责识别媒体引用、解析安全本地路径、判断文件存在性和类型、提取纯文本附件、按完整消息边界分块、校验 JSON 结构并原子写文件。
- Gemini 负责理解图片/PDF、生成媒体文字说明、总结单块语义，以及在多块时按主题合并。
- 媒体说明必须回填到原消息附近，再参与对话总结。文件缺失、失效或格式不支持时必须明确写“未能成功提取内容”，不能让模型猜测。
- 单条消息超过分块上限时才允许在消息内部按段落切分；普通情况优先保持用户提问与 AI 回答的边界。
- 最终 JSON 的 topics 带稳定 topic_id，typed_records 保留任务专用结构，为以后用户选择重要部分预留接口，但当前版本不加入选择 UI。

Gemini 属于显式可选步骤。普通 parser.py 和 run_tests.py 不得默认调用 API，以免网络、额度或模型变化破坏原有抓取回归；只有 --summarize 或 summarize_memory.py 才允许上传对话。API 失败时必须保留已经正确生成的原始 Markdown。

任何 API 层改动除离线单元测试外，仍要完整运行原有 run_tests.py，并按 results_right 的规则核对消息数、正文、图片数和超长对话抽样，证明平台提取结果没有回归。
补充教训：ChatGPT 的图片和超长正文都存在延迟挂载竞态。逐屏采集时不能只保存消息第一次出现的 outerHTML，否则首屏图片或后加载的长代码会永久丢失。当前做法是在每个位置复采并回访列表首尾；只有当候选快照的正文长度或真实图片数变多、且另一维不退步时才替换旧快照。不要简单按 HTML 长度替换，因为后加载的按钮和工具栏也会使 HTML 变长并污染正文。

Gemini 默认模型选择历史（2026-08-11，已被 2026-08-12 记录取代）：当时当前 Key 调用 gemini-2.5-flash 返回 404 NOT_FOUND，而 gemini-3.6-flash 真实请求成功，因此曾临时使用 3.6 Flash；这不是永久结论，现行默认值见下文第 10 节。选择长期默认模型仍应优先使用 Google 标记为正式可用（GA）、支持所需多模态能力的固定模型名；不要默认使用 Preview、Experimental 或 latest 别名。必须保留 GEMINI_MODEL 和 --model 覆盖入口，不得在业务调用点重复写死模型名。
总结产物目录约定补充（2026-08-12）：Gemini 的默认结构化结果和可读总结统一写入项目的 summary 目录，并按输入 Markdown 的文件名分别命名为“源文件名_result.json”和“源文件名_summary.md”。不同对话不得继续共用根目录中的 AI_memory_result.json 或 AI_memory_summary.md，以免覆盖后无法判断结果来源；summary 属于本地检查产物，应保持在 .gitignore 中。显式传入 --json-output 或 --markdown-output 时仍允许用户选择其他路径。
总结展示层级反馈补充（2026-08-12）：分层不是分类越多越好。关键点与重要细节应合并为统一的内容要点；决定、未决事项和后续建议应放回相关主题语境，不能机械生成独立板块。短对话默认只展示总览，程序必须在模型返回冗余 sections 时执行确定性折叠；长对话也只有存在多个真正独立主题时才分区。媒体与附件说明目前保留并标记为“开发检查”，便于验证多模态识别，未来面向普通用户时再提供隐藏或显示选项。

批量总结入口约定：summarize_tests.py 直接读取 tests.txt 对应的现有 results 并调用 Gemini，不重新抓网页；run_tests.py --summarize 先重跑全部测试链接，再调用前者总结。缺少用户或 AI 任一角色的无效抓取结果必须记录为跳过，不能生成看似正常但内容错误的总结。

9. 可续接记忆结构约定（2026-08-12）
总结结果使用 schema_version 8（旧版结果可通过 renormalize_result 做确定性兼容处理）。总览优先回答当前在做什么、做到哪一步、用户是否真的执行、下一步和断点状态；不能只回顾历史主题。每条 claim 和细粒度记忆必须显式携带 source、status、message_ids 与由程序确定性生成的 message_range。AI 的诊断、预测和方案在没有用户验证时只能标为 suggested、assumed 或 uncertain，不能因为语气肯定就变成事实；AI 已实际给出回答或代码但用户没有确认采用时使用 delivered。

程序必须保留全部用户原始查询索引，并保留最后 20 条消息（最多最近 10 轮）的高保真上下文。模型负责生成语义记忆，但搜索兜底和最近上下文由程序生成，不能依赖模型是否“觉得重要”。短消息如 1、继续、这个怎么改必须保留原文并绑定上下文；无法确定指代时明确标 uncertain。

不同任务使用不同记录：编程区分代码现状、约束、Bug、上一 AI 诊断、已实施和待验证；学习纠错保留用户原句、AI 修改、理由和用户是否采用；计算分开用户条件与 AI 自行假设；决策保留候选、用户选择和状态。主题内部要记录条件变化如何改变结论，不能只留最终答案。

原文疑似错误不能静默修正。应保留 original_text，将可能修正写入 inferred_correction，并标 inferred/uncertain。例如同一回答重复 500MB 以下、后续解释却冲突时，可以推测第二处可能是 500MB 以上，但不能覆盖原文。

媒体记录必须绑定用户消息、随后 AI 结论和可访问性。当前本地文件可标 can_reverify=true；分享页原图失效或未下载时必须写明不能重新验证，上一 AI 的视觉结论只是历史陈述。豆包文档卡片中的 Asset cover、base64 封面和 doc-canvas-card-fallback 是界面装饰图，不是用户上传图片；只有成功下载的真实图片才进入图片列表。旧导出若只有用户消息中的独立 .docx/.pdf 文件名，应作为不可访问文档保留，不能猜内容。

10. Gemini 限流与恢复约定（2026-08-12）
当前默认模型为稳定版 gemini-3.5-flash，但仍必须支持 SUMMARY_PROVIDER、SUMMARY_MODEL、旧 GEMINI_MODEL 和 --provider/--model 覆盖。2026-08-16 实测 gemini-3.5-flash 与 gemini-3.6-flash 均可调用；本轮 3.5 在 DeepSeek 超长对话第 4/10 块遇到 429，随后显式用 3.6 仅补跑该文件成功。额度状态不是永久结论，业务代码不得静默换模型。用户明确允许时，SiliconFlow 的 Qwen/Qwen3.5-397B-A17B 可作为备用后端。

分块上限当前默认 24000 字符，结构化输出上限默认 16384，Gemini 3 的思考等级默认 medium，均允许环境变量覆盖。每个媒体说明和分块结果写入 *_progress.tmp 恢复缓存，指纹必须包含后端、模型、分块配置和原消息；成功写出最终结果后删除缓存。429 重试至少等待一个限额窗口，批处理任务之间留间隔，避免快速重试耗尽配额。异常展示必须脱敏两类 API 密钥，进度缓存、summary 和密钥文件继续保持在 .gitignore 中。
11. 编程对话分类约定（2026-08-13）
编程对话必须先区分“真实开发任务”和“编程学习”：代码块本身不能证明用户在维护项目。学习概念、理解教学示例、询问语法/原理时使用 programming_learning，示例中的代码事实使用 learning_point，并在可读结果中显示为“编程学习记录/学习要点”；只有实际实现、修改、调试、测试或部署才使用 programming/code_state。模型提示负责首轮判断，程序还要结合当前活动、用户意图和执行证据做一致性兜底，避免分类标签与总览自相矛盾。

12. 总结语义质量兜底约定（2026-08-13）
Gemini 输出不能直接视为可靠状态。混合引用一组用户/AI 消息时，程序必须按实际角色缩小 message_ids，并区分“用户提出”“上一 AI 已交付”和“用户已经采纳/执行/掌握”；AI 已给出回答或代码用 delivered，不能据此生成用户 confirmed/executed/verified。多轮学习中“AI 已讲解”不能自动变成“用户已掌握”。未确认代码只能列为 AI 已提供/建议，不能显示成已实施。

历史对话不是总结模型正在参与的新会话。必须在系统、分块和综合提示中明确：输入是已经发生过的用户—AI 对话，目标是生成续接记忆，不是继续回答用户。AI 回答末尾“如果你愿意，我还可以……”“是否需要我继续……”等平台式礼貌延伸，默认不是待办、决策或断点；只有用户后续明确接受，或追问是完成原任务必需的澄清时才保留。普通事实问答、翻译、解释和识别使用 answered（已回答），不存在“等待用户采纳”；delivered 主要用于代码、文稿、方案等确实可能需要采用的交付物。

编程记录必须分开保存 assistant_proposed_changes、implemented_changes 和 implementation_status。用户在收到代码后报告运行时报错，可以标 attempted_by_user，但不能反推所有修改均已采用或最终成功。若计算结果出现来源消息中不存在的数字，只标低可信仍不够：必须从正式可读结果中移除模型生成结果，并保留被拒绝内容供开发检查。

短对话不能再仅按总字符数删除全部主题；单轮极短对话可只保留总览，多项互不相关任务必须保留主题。多分块综合后要检查 memory_ids 覆盖，不能只留下最后一块。计算结果中的数字必须能在所引 AI 原文中找到，否则标记 unsupported_numbers 并降低可信度。编程语境中的“PDF 翻译、Python、API、并发、报错”等不得被词汇聚合器误判为英语学习。只有“上传文件/上传文档”占位时也要保留不可访问附件记录。批量报告必须写实际模型，并明确它只证明执行状态，不等于语义验收通过。

13. 超长对话聚合与输出一致性约定（2026-08-13）
分块最小语义单位是一个用户消息及其后紧随的 AI 回答。普通轮次不能在角色边界中间切开，否则“用户新增条件”会和上一轮旧答案落入同一批，最终造成条件—结果错配；只有单个完整轮次本身超过上限时，才允许退回消息或段落级切分。

自然语言学习聚合必须采用正向证据。不能因为整个分块以英语学习为主，就把 fact、user_condition、assistant_suggestion 等所有剩余记忆自动算作词汇；行政区划、中文材料撰写、文档、媒体、计算与编程必须排除并恢复独立主题。语言主题只能承诺保留代表性细节，不能声称全部内容都在可读“细节记忆”中。

同一计算主题存在多轮条件更新时，可读计算记录优先保留最新条件及其紧随回答；旧条件与旧结果可在递进记录中留痕，但不得把新条件拼到旧结果上。数值出现在某条旧回答中并不足以证明条件绑定正确。

所有可读字段都必须为简体中文。若模型仍返回整段英文，总览和当前状态要由程序降级为中文安全文案。细节记忆中来自 AI 且状态为 answered 的事实叫“上一 AI 回答”，suggested/delivered 叫“重要建议”，不能统一提升为“重要事实”。批处理开始时应清理旧版带模型名的遗留进度缓存，但保留当前 *_result_progress.tmp 以便断点恢复。

普通版和带细节版不能对同一原文各自独立调用模型，否则随机性会造成核心主题、语言和事实不一致。结构化结果必须保存原文指纹；详细版只要找到同 schema、同原文指纹的普通版 JSON，就复用其中记录的实际后端与模型，只增加细节展示，不因命令行请求模型不同而重复调用。resume 模式跳过 API 任务时才要求实际模型也匹配。

14. Schema 8 终极质量兜底约定（2026-08-16）
总结模型只负责提出候选语义，程序必须负责最终一致性。Schema 8 对以下问题执行确定性修正：最后用户意图与随后 AI 回答按角色拆开；已回答的普通问答不等待用户开启新话题；AI 普通建议不重复列入 pending；用户没有自述理解、掌握、采用或执行时不能替用户确认；不可访问媒体的主题和总览必须明确只是历史 AI 判断。

自然语言学习必须使用强正向证据并让代码语境优先排除。明确的“英文、英语、翻译、词汇、语法”请求可以连同相邻回答并入语言主题；PDF、API、ThreadPoolExecutor、future.result、脚本与代码修改不因出现“翻译”二字就进入语言学习。一个连贯开发任务若被模型拆成四个以上实现小节，且所有小节都具有编程证据，应合并为一个开发主题；多个真正独立任务仍分别保留。

语言学习 JSON 可以保留全部结构化记录，但 Markdown 最多展示 8 条代表项，并优先保留明确纠错；详细版额外细节同样最多 8 条。原文问题板块只保留语义冲突、影响判断或可能造成执行错误的实质问题，姓名拼写、普通错别字等简单笔误不单独输出。用户事实默认显示为“用户信息”；只有要求、限制、条件或排除项才显示为“用户约束”。

模型后端统一通过 SummaryGateway 接口接入。Gemini 使用官方 google-genai SDK 和可配置 thinking_level；SiliconFlow 使用 /v1/chat/completions、JSON Schema 输出与 Qwen3.5 可配置模型。缓存指纹必须包含 provider 与 model，错误信息必须同时脱敏 GEMINI_API_KEY、Silicon_API_KEY 和 SILICONFLOW_API_KEY。

15. 极简版总结约定（2026-08-20）
极简版是普通版、详细版之外的独立展示链路。simple_summarizer.py 只复用同 schema、同原文指纹的普通版结构化 JSON，不修改 gemini_summarizer.py 的普通版/详细版生成和渲染逻辑；summarize_tests_simple.py 只负责批量生成 summary_simple。summary_simple 是本地人工检查产物，必须保留在 .gitignore 中。

极简 Markdown 只能包含一个“总览”标题和一个中文段落。总览合并真正有续接价值的用户目标、约束、上一 AI 已交付的关键结论及真实未决事项；媒体开发说明、质量报告、普通寒暄、平台式追问和“等待/接收新指令”等客套收尾均不输出。程序必须校验长度、单段结构、数字来源、角色归属、虚假采纳与虚假待办，并保留“约、可能、历史 AI 判断”等必要不确定性。

超长语言学习对话在极简版只保留整体学习范围，不能随机枚举词汇、短语、谚语、术语或最后一个低价值短查询。纯学习主题通过 memory_id 与 learning_point 的结构化关联过滤，不使用容易误删计算、媒体或编程任务的关键词猜测；计算、决定、编程断点及不可复核媒体等独立主题仍应保留。模型额度不足时，极简批处理可按用户授权在 Gemini 3.6 Flash、3.5 Flash、3.5 Flash Lite 及配置密钥后的 SiliconFlow Qwen 之间回退；--repair-existing 必须保持零 API，只做确定性规范化和校验。
