📈 1. 进程总结
初始目标与尝试：从“先不考虑形式，先跑通功能”出发，使用 Python 编写自动化脚本来抓取 AI 共享对话链接中的内容。
技术选型与实现：选用了 Playwright 搭配 BeautifulSoup 来抓取和解析动态网页内容。
问题解决与迭代：
解决图片抓取与渲染问题：早期遇到过豆包的图片成功保存到本地 images 文件夹中、但未能在 Markdown 中正确渲染的问题，随后修复了图片提取逻辑。
解决抓取超时问题：在抓取 ChatGPT 页面时，使用 Edge (msedge) 作为浏览器内核时遇到长达 180s 的启动/网络等待超时。随后切换为 Playwright 默认的无头 Chromium 模式，并修改了等待策略，问题得以解决。
兼容多平台：在原有豆包抓取的基础上，加入了对 ChatGPT 链接格式的兼容。
成果输出：生成了高质量的 AI_memory_export.md 文件，成功将对话分离成了“👤 用户”与“🤖 AI 回答”，并能将历史对话、包括讨论课个人作业的分析结果都留存记录下来。最后进行了 Git 提交（包括“支持图片”、“支持豆包和ChatGPT”、“删除无用文件”等 commit），并合并到了 main 分支。
💡 2. 经验总结
规避 networkidle 陷阱：在抓取现代单页应用 (SPA) 如 ChatGPT 时，由于后台长连接的存在，依靠 wait_until="networkidle" 往往会导致超时。我们在代码中加入了 Try-Except 进行优雅降级，当网络等待超时时程序能继续往下走。
基于 DOM 元素的等待更加稳定：我们发现通过等待特定的 CSS 选择器（如 page.wait_for_selector(".message-item, [data-message-author-role]")）出现，比单纯等待网络状态更为可靠且高效。
清晰的数据结构是后续处理的前提：将爬取下来的无序 HTML 节点依据 data-message-author-role 进行角色切分，然后统一映射到 Markdown 模板中，这种模块化的数据清洗方式非常便于后续将内容输入给其他 AI 去做进一步的总结和分析。
⚠️ 3. 教训与反思
依赖浏览器的自动化比较脆弱：由于直接依赖 Playwright 模拟浏览器行为，一旦官方页面（如 ChatGPT 或 豆包）的 DOM 结构或者 Class 命名发生改变，解析器（parser.py）就极易失效，需要经常维护。后续（正如工作文档中所提）需要探索直接使用官方 API 来拉取对话数据，这才是最稳定的长期方案。
本地路径与相对路径的引用坑：在处理多媒体（如抓取下来的图片）时，Markdown 中的图片引用稍有偏差（比如漏掉相对路径的层级），就会出现“图片在硬盘上但 Markdown 渲染不出来”的现象，处理静态资源链接时必须格外严谨。
总体而言，那是一次非常高效的原型开发（Proof of Concept）过程。虽然存在一些自动化的坑点，但最终成功实现了核心链路，并输出了格式优美的对话记忆记录。
4. 你还要记住，ChatGPT是滚动到对应位置才把对话渲染出来，我们之前尝试过使用超长窗口解决该问题，但这又导致用户登录时浏览器显示错位，我们解决这个问题的办法是对视口（Viewport）的大小进行条件判断，根据“是否需要用户手动登录”来动态设置窗口高度：登录模式下使用默认正常窗口： 当我们检测到处于需要手动登录的模式（need_login = True，此时浏览器是带有 UI 界面的）时，我们会将 viewport_config 设为 None，并在 Playwright 启动参数中传入 no_viewport=True。这会让浏览器以默认大小和原生视口启动，从而保证网页的 UI 和登录弹窗正常居中，不会发生错位。
抓取模式下使用超高虚拟窗口： 当我们处于后台静默抓取模式（headless=True）时，我们不需要考虑登录界面的美观，只需要让 ChatGPT 以为我们在往下滚动从而把历史记录都渲染出来。因此此时我们会强制设置 viewport={'width': 1920, 'height': 10800}，将页面视口拉得极高，一次性把通过虚拟列表（Virtual List）隐藏的聊天内容全部“挤”进渲染流里。

7. 平台适配器模块化约定（2026-08-11）
为了避免所有平台逻辑继续堆积在 parser.py 中，ChatGPT、DeepSeek、豆包已经迁移到 providers 目录。parser.py 只负责浏览器启动、页面加载、通用图片下载、平台调度、降级解析和命令行入口；markdown_exporter.py 统一负责终端展示与 Markdown 导出。

每个平台模块统一提供以下成员：
- DISPLAY_NAME：终端显示的平台名称。
- WAIT_SELECTOR：判断动态消息节点是否出现的稳定选择器。
- parse_messages(soup, image_map)：识别并解析该平台；不属于该平台时返回 None。
- collect_html(page)：仅虚拟列表平台需要实现，用于逐屏采集完整消息。

新增 AI 时，应在 providers 中新建独立文件，再在 providers/__init__.py 中导入并加入 PROVIDERS。平台检测顺序由 PROVIDERS 决定；当前顺序必须保持为 ChatGPT、DeepSeek、豆包，除非有充分测试证明可以调整。不要把新平台的 CSS 选择器、附件规则或消息清洗逻辑重新写回 parser.py。

模块拆分属于纯重构时，必须完整运行 run_tests.py，并与 results_right 中的黄金基线比较。图片链接可能包含动态签名，不能只比较原始文件哈希；应同时比较问答数量、忽略本地图片文件名后的正文、图片文件是否存在，以及超长对话的首尾和多个中段抽样点。
